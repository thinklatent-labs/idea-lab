# Taking the portal into the real environment

Written 18 Nov 2026 for the engineers who continue this work. It says what exists, how to run it, what to do first in
the environment, and what is not finished. Everything in the thinklatent-labs organisation is private.

## 1. What you are getting

One repository, one branch to start from: **`backend-integration`**. It holds both halves.

| Part | Where | State |
|---|---|---|
| The screens | `apps/portal` (React, TypeScript, Vite, the design kit in `vendor/design-kit`) | 145 addresses, the design locked on 17 Nov (branch `ui-lock-2026-11-17`). They still read the sample world, not the service. |
| The service | `services/api` (Node 22, TypeScript) | 455+ endpoints in ten areas, sign-in by OpenID Connect, audit, paging, live events, background workers, service accounts |
| The contract | `packages/contract` | Every endpoint defined once (zod); a typed client for the screens |
| The database | `db/migrations/<area>/*.sql`, `db/seed` | Postgres 16, ten schemas (core, org, work, catalogue, delivery, tlindex, data, training, metrics, try); plain SQL, forward-only |
| Try TLM's store | `services/api/src/areas/try/store` | 24 Amazon DocumentDB 5.0 collections with validators, indexes and an installer. **Never run on a real cluster.** |
| The sample world | `packages/scenario` | Made-up data. It seeds a development database and is the tests' fixture. Never load it in production. |
| Documents | `docs/backend/` (plan, install, conventions, api, one per area), `docs/requirements/` | See section 6 |

Other branches: `main` (build 4 of the screens, older), `integration` and `ui-lock-2026-11-17` (the locked screens
without the backend), `home-trial` (a rejected redesign; do not merge).

## 2. Run it on a laptop

Node 22+, pnpm 10, Postgres 16 (no extensions, no Docker needed).

```sh
git clone <the portal repository> && cd portal && git checkout backend-integration
pnpm install
pnpm db:start            # a local Postgres 16
cp services/api/.env.example services/api/.env
pnpm db:migrate          # installs every schema
pnpm db:seed             # the sample world (development only)
pnpm api:dev             # the service on :8787, a stand-in sign-in on :8788
pnpm dev                 # the screens (separately; they do not call the service yet)
```

Checks before any push:

```sh
pnpm -r typecheck && pnpm --filter api test        # 687 tests; they start their own Postgres
pnpm kit:check && pnpm licences && pnpm check:usable && pnpm check:representation && pnpm coverage && pnpm -r test
```

`pnpm kit:check` fails in a fresh clone until the kit's token stylesheet is built
(`vendor/design-kit/packages/tokens/dist` is not committed): run `pnpm kit:pull --with-motion` with a design-kit
checkout beside this repository, or build the tokens package once.

## 3. First steps in the environment, in order

Follow `docs/backend/install.md` section 3; `docs/requirements/backend-setup-checklist-2026-11-16.md` lists what to
ask each team for.

1. **Sign-in.** Register the portal with the Enterprise's single sign-on (OpenID Connect, authorisation code with
   PKCE). Create the groups: `foundation`, `index`, `ai-engineering`, `product-adoption`, `risk-audit-readonly`.
   Set `OIDC_*` and the group claim in the service's environment.
2. **Postgres 16** (RDS or Aurora). Two roles: an owner for migrations, `portal_app` for the service (row-level
   security depends on the service not being the owner). Run `pnpm db:migrate`. Do not run `db:seed`.
3. **Run the service** (`pnpm api:build`, then the one file with `pg` and `mongodb` beside it) behind TLS; check
   `/healthz` and `/readyz`. `/readyz` lists every outside connection and whether it is still a stand-in.
4. **DocumentDB 5.0, instance-based** (not elastic). Run `pnpm try:cluster-check` first, then `pnpm try:install`.
   Steps and what each proves: `docs/backend/areas/try-cluster-checklist.md`.
5. **Replace the stand-ins**, one file each (`docs/backend/install.md` 3.5.1 lists all of them with their settings):
   the request store reader, the change system, Jira, the incident tool, the access system's registrations, Slurm,
   the training store, self-healing, the Index runner, exports, the agent runtime, and for Try TLM the model call,
   the client-data check, object storage and connector sign-in. In production the service refuses to start on a
   stand-in unless `ALLOW_STAND_INS` names it.
6. **Service accounts** for the training job and the Index runner (`SERVICE_CLIENTS`, client credentials).
7. **Connect the screens** (section 4, item 2).

## 4. What is not finished (do these next)

1. **The production build guard fails.** `pnpm api:build` stops with "The production build must not contain…":
   several stand-ins and seeds import the sample world, so it would be bundled. Fix: stand-ins load the world lazily
   from a file path outside the bundle (or are left out of the production entry), then the guard passes. Until then
   run the service with `pnpm --filter api start` from source, in lower environments only.
2. **The screens do not call the service (plan build B9).** Each page imports the sample world directly (165 files).
   Replace per area: a query function per question in `apps/portal/src/data/queries/` calling the typed client in
   `packages/contract`, with loading, empty, error and no-access states. Keep the sample world as demo mode behind
   the same functions. No screen should change how it looks.
3. **Split the web bundle by area** (one 9.2 MB file today) and move from hash addresses to normal ones.
4. **An independent review of security and speed** has not been done on the merged whole. Each area proved its own
   row-level security and query plans at 100 times the sample size; nobody has reviewed across areas.
5. **The UI evaluation** (`docs/requirements/ui-evaluation-2026-11-18.md`, 146 findings: focus ring, tab contrast,
   table structure for screen readers are the three critical ones) is not marked or applied.
6. **Open product questions for the Head of ThinkLatent**: a role for "the foundation lead" and for his own
   sign-off; about 30 places where the sample world contradicts itself (each area's document ends with its list);
   whether a person is keyed by the sign-in's subject (built) or by email.
7. **Not provable outside the environment**: DocumentDB itself, every real connection, real sizes and timings.
8. **Model calls** (the playground's live answer, the agents' words, scoring) were out of scope by decision and are
   seams with stand-ins.

## 5. Rules that carry over

- Never write the employer's name in code, data or documents: "the Enterprise". ThinkLatent is spelled out. Brand
  words are configuration.
- Numbers on screens come only through the kit's number helpers; kit components and tokens only; never edit
  `vendor/design-kit`. See `CLAUDE.md`.
- Backend: `docs/backend/conventions.md` — one schema and one folder per area, plain-SQL forward-only migrations,
  keyset paging, an index for every filter and sort, row-level security proven by a direct SQL test, every one-way
  door writes its change, a `work.decision` and an audit row in one transaction, every outside system is one seam.
- Sealed production text is never readable by the portal (D-324). Connectors store no keys (D-412).
